# 动态层级分类协议

分类列在分析过程中长出来，不预先锁死。列一旦长出，后面的 review 优先复用，对不上再加列。

## 列名

```
极性|一级分类|二级分类
极性|一级分类|二级分类|三级分类
```

例：

- `差评|质量差|工作几次就坏了`
- `好评|功能表现很好|贴边修剪干净`
- `差评|质量差|工作几次就坏了|雨后轮毂轴承进水卡死`（仅当二级仍太粗、且这个细节会反复出现时）

单元格里只放**买家原文摘录**，不放改写、不放翻译。同一格多条摘录用 ` | ` 连接。

## 三级怎么分

按指南的递增分类，不要拍平。

| 层级 | 作用 | 增长速度 | 写法 |
|---|---|---|---|
| 一级 | 粗维度，给后面聚类当大桶 | 很慢 | 短、稳定、带极性。差评如「质量差」「功能差」「续航与覆盖差」；好评如「功能表现很好」「使用省心」「导航建图好」 |
| 二级 | 主分析颗粒。同一类问题的具体表现 | 中等 | 一句话点明表现，贴近指南例子：「材质质量差，工作几次就坏了」「吸力很强，清洁效果很好」 |
| 三级 | 二级内部的可聚类细节 | 持续分析时才频繁增加 | 只写比二级更窄的条件/部位/场景。一般不建议先开 |

判断落在哪一层：

1. 先找一级：这个点属于哪一种好坏。
2. 再找二级：它具体是哪种表现。二级是默认落点。
3. 只有「同一二级下已经能看出两种会分开用的子情况」才开三级。例如二级已是「复杂地形易卡顿」，再出现大量「湿草卡刀」和大量「树根卡轮」且后面要分开看，才拆三级。

不要：

- 用一级列当落点（一级只挂载，不单独成列）
- 把整段 review 塞进一个列
- 把同义措辞开成新列（battery dies / needs frequent recharge = 同一二级）
- 为了整齐把不同语义硬塞进已有列

要：

- 一条 review 可以同时进多个好评列和多个差评列
- 辩证评论必须两边都摘
- 新列可追溯：taxonomy 记录 first_row_id / first_asin / first_excerpt
- 近义合并只并列、不删摘录

## 单条处理顺序

1. 只精读 `标题` + `内容`。星级只作参考，不替代文本。
2. 拆好评点 / 差评点。无有效信息 → `sentiment_mix=信息不足`，不加列。
3. 每个点对照**当前 taxonomy**：
   - 语义已有列 → 把原文短摘录写入该列
   - 只有一级能对上、二级对不上 → **在该一级下新建二级**
   - 一级也对不上 → **新建一级 + 二级**
   - 已有二级过粗、本条细节后面要单列聚类 → 新建三级
4. `sentiment_mix`：只有好评 / 只有差评 / 两边都有=混合 / 无可摘信息=信息不足
5. 摘录尽量短、可独立阅读，保留原语言。不要把无关句子拷进去。

## 新列是否该开

开：新的语义类型。关：新的措辞、程度词、同一故障的同义描述。

| 开新二级 | 并入已有二级 |
|---|---|
| 贴边漏割 vs 中间漏草 | 续航短 vs 大草坪要回充 |
| 建图失败 vs 运行中丢定位 | App 卡 vs App 难用（先并，除非操作路径明显不同且量大） |
| 售后不回 vs 配件长期缺货 | 噪音大 vs 晚上太吵 |

一级应长期保持少而稳。一个类目做完，好评一级、差评一级各自通常个位数到十来个，不是几十个。

## 近义对齐（波次边界做，不是预先锁死）

1. 列出本波新增 `col_key`
2. 与已有二级比：同一极性 + 同一一级 + 可互换语义 → 合并到先出现的列
3. 把被合并列的摘录追加到保留列，taxonomy 标记 `status=merged`，`merged_into=保留列`
4. 不合并跨一级、不合并好坏相反的列
